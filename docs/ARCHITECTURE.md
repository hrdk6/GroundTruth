## Configuration model

Two kinds of configuration, deliberately separated:

| | `app/core/settings.py` | `app/core/pipeline.py` |
|---|---|---|
| Holds | secrets, hosts, log level, cache dir | chunker, k values, models, prompts, toggles |
| Source | `.env` / environment | `configs/*.yaml` |
| Committed | no | yes |
| Changes between | machines | experiments |

An experiment is reproducible from `(config hash, git SHA, dataset version)`.
`PipelineConfig` is frozen and hashed on its resolved values, so reformatting a
YAML file does not invent a new config while changing `k` does.

## Decisions

Each entry: context, choice, trade-off.

### D1 — Postgres for vectors, text, metadata, and traces

**Context.** The system needs dense vectors, lexical search, metadata filtering
by version, and trace storage. The default industry answer is a dedicated vector
database plus a separate search engine plus a tracing backend.

**Choice.** One Postgres 16 with `pgvector`. HNSW for embeddings, `tsvector` +
GIN for full-text, JSONB for span attributes.

**Trade-off.** Postgres full-text search uses `ts_rank_cd`, which is *BM25-like*
but not BM25 — no proper IDF saturation or length normalization, so lexical
results will be slightly worse than a real BM25 engine. Accepted because a
single store means one migration path, one backup, atomic version filtering as a
SQL pre-filter instead of a post-filter, and no cross-store consistency problem.
ParadeDB's `pg_search` is the upgrade path if lexical recall proves to be the
bottleneck; that would be an experiment, not an assumption.

### D2 — Local embedding and reranking models

**Context.** Evals re-run constantly. API-based embeddings would make every
re-ingestion and every retrieval experiment cost money and vary over time.

**Choice.** `bge-small-en-v1.5` (384-dim) for embeddings and
`bge-reranker-base` for cross-encoder reranking, both local and CPU-only.

**Trade-off.** Lower ceiling than a large API embedding model, and a ~2GB
dependency footprint (torch). Bought: retrieval evals run in CI with no API key,
cost nothing, and are deterministic. The embedding model is a config field, so
"does a bigger embedder help?" stays answerable as an experiment.

### D3 — One LLM client with a persistent cache

**Context.** The eval loop re-runs the same prompts constantly, and cost is a
first-class constraint.

**Choice.** Every model call goes through `LLMClient`, which caches responses on
disk keyed by `(model, prompt, params)` and records tokens and dollars per call.

**Trade-off.** A cache hit reports `cost_usd = 0.0`, so a re-run honestly
reports ~$0 rather than a hypothetical cost — `list_cost_usd` keeps the list
price for reference. The cache also carries a real hazard: it will happily serve
a response generated by an older prompt if the prompt text is unchanged.
`CACHE_VERSION` exists to invalidate wholesale when the payload shape changes.

### D4 — Chunk identity includes the chunker's parameters

**Context.** Comparing chunking strategies means having several chunkings of the
same corpus in the database at once.

**Choice.** `chunks.chunker_name` is `"{strategy}-{max_tokens}-{overlap}"`, not
just the strategy name, and retrieval always filters on it.

**Trade-off.** More rows and a larger index. Bought: switching chunkers is a
config change rather than a re-ingestion, so a chunking experiment is cheap
enough to actually run.

### D5 — Generation is not bit-reproducible; the cache is what makes evals stable

**Context.** Claude 4.6 and later removed sampling parameters — sending
`temperature` to `claude-sonnet-5` returns a 400.

**Choice.** `LLMClient` drops `temperature` for models that reject it, logging
at debug level, and keeps the field in `PipelineConfig` for models that accept
it.

**Trade-off.** Two identical eval runs against a cold cache can differ slightly.
Reproducing a published number therefore means reproducing it *with the cache*,
or accepting run-to-run noise. This is a real limitation and is recorded in
`docs/LIMITATIONS.md` rather than papered over.

### D6 — Windows dev machine, Linux-shaped tooling

**Context.** The primary dev machine is Windows without GNU make; CI is Linux.

**Choice.** `Makefile` is the reference; `make.ps1` mirrors it for PowerShell.
Postgres only ever runs in Docker.

**Trade-off.** Two files to keep in sync, which is a real maintenance cost and
is flagged in `CLAUDE.md`. The alternative — requiring MSYS/Chocolatey make —
adds a setup step for every reader of the repo.
